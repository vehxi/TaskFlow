# Логическая модель данных

Модель разработана по [требованиям](requirements.md), [матрице прав и жизненному циклу](explanatory-note.md) и [сценариям UC-01–UC-14](use-cases.md). Она определяет сохраняемые факты без привязки к типам конкретной СУБД. Это проектное решение для последующей реализации.

## Сущности и атрибуты

Идентификаторы однозначно различают объекты. Все перечисленные атрибуты обязательны; описание проекта и задачи допускает пустой текст. Технические версии и временные метки конкретизированы в физической модели.

| Сущность | Идентификатор | Сохраняемые атрибуты и назначение |
| --- | --- | --- |
| Пользователь | Идентификатор пользователя | Имя, уникальный нормализованный email, хеш пароля, признак активности. Исходный пароль не хранится. |
| Роль | Код роли | Фиксированные значения ADMIN, MANAGER, EXECUTOR; состав ролей не является настраиваемым справочником. |
| Назначение роли | Пользователь + роль | Связь пользователя с каждой из его ролей; пара уникальна. |
| Проект | Идентификатор проекта | Название, описание, единственный руководитель. |
| Участие в проекте | Проект + пользователь | Действующее участие, дата включения. Пара уникальна. |
| Тип задачи | Идентификатор типа | Название, уникальное внутри справочника, признак активности. |
| Приоритет задачи | Идентификатор приоритета | Название, уникальное внутри справочника, признак активности. |
| Задача | Идентификатор задачи | Проект, автор, текущий исполнитель, название, описание, срок, статус, тип и приоритет. |
| Комментарий | Идентификатор комментария | Задача, автор, текст, момент создания. |
| Запись времени | Идентификатор записи | Задача, автор, календарная дата работы, целое положительное количество минут, момент создания. |

У пользователя есть минимум одна роль. Назначения ролей образуют связь многие-ко-многим; назначение роли не дублируется в записи пользователя. Одновременные роли руководителя и исполнителя поддерживаются без дополнительных учётных записей.

## Связи и обязательность участия

[Диаграмма доступа и проектов](diagrams/logical-access.md) и [диаграмма задач и учёта](diagrams/logical-tasks.md) являются двумя представлениями одной модели. Пользователь и проект на второй схеме повторены как точки связи.

| Связь | Кардинальность и обязательность |
| --- | --- |
| Пользователь — назначение роли — роль | У пользователя 1..* назначений, каждое относится к одному пользователю и одной роли. Роль может не иметь пользователей. |
| Пользователь — проект под управлением | У пользователя 0..* проектов, у проекта ровно один руководитель. |
| Пользователь — участие — проект | Пользователь участвует в 0..* проектах; проект содержит 0..* участников; каждое участие относится к одному пользователю и одному проекту. |
| Проект — задача | Проект содержит 0..* задач; задача относится ровно к одному проекту. |
| Пользователь — задача как автор | Пользователь создаёт 0..* задач; у задачи ровно один автор, который при создании является руководителем проекта. |
| Пользователь — задача как исполнитель | Пользователю назначено 0..* задач; у задачи ровно один текущий исполнитель. |
| Тип / приоритет — задача | Значение может не использоваться или использоваться многими задачами; у задачи ровно один тип и один приоритет. |
| Задача — комментарий / запись времени | Задача имеет 0..* записей каждого вида; каждая запись относится ровно к одной задаче. |
| Пользователь — комментарий / запись времени | Пользователь является автором 0..* записей; у каждой записи ровно один автор. |

Руководитель не обязан быть исполнителем-участником: связь управления независима от состава участников. Для назначения задачи себе руководителю нужны роль исполнителя и собственное участие в проекте.

## Назначение и история

Текущий исполнитель задачи ссылается на пользователя, а не на запись участия. BR-02 требует действующего участия при создании, переназначении, начале работы и повторном открытии. Но после закрытия задачи пользователя можно исключить из проекта или лишить роли; историческое назначение должно сохраниться. Поэтому обязательная связь задачи с текущим участием ошибочно запрещала бы допустимое исключение участника.

Запись участия удаляется при разрешённом исключении; пользователь при этом сохраняется. Незавершённые задачи предварительно переназначаются. Блокировка меняет признак активности пользователя и не удаляет участие или назначение. Для повторного открытия закрытой задачи с недействующим назначением руководитель выбирает подходящего исполнителя в той же операции.

Автор задачи, авторы комментариев и записей времени не меняются при переназначении. Автор времени не выводится из текущего исполнителя. Отдельная история всех переназначений не вводится: обязательные требования предусматривают сохранение текущего назначения и авторства исходных записей.

## Нормализация и вычисляемые данные

Модель организована в третьей нормальной форме: характеристики пользователя хранятся у пользователя, проекта — у проекта, типа и приоритета — в соответствующем справочнике. Связующие сущности имеют составные ключи; дублирующие списки ролей и участников в других объектах отсутствуют.

В комментариях и записях времени не дублируется проект: он определяется через задачу. У задачи нет копий email исполнителя, имени автора или названия проекта. Статус — одно из четырёх фиксированных значений, а не редактируемый администратором справочник.

Прогресс, признак просрочки, сумма времени и отчётные итоги вычисляются из исходных записей по BR-04–BR-06. Для них не создаются отдельные таблицы или изменяемые счётчики. Файл Excel формируется по запросу. Это исключает рассогласование итогов при изменении статуса или исполнителя.

Письмо формируется после сохранения бизнес-операции. Обязательная версия не предусматривает очередь, автоматические повторы или историю писем в интерфейсе; отдельная сущность уведомления не требуется. Результат отправки фиксируется в журнале приложения без секретов, доставка проверяется почтовым приёмником. Механизм отправки конкретизируется при проектировании архитектуры.

## Доменные классы

[Пользователи и проекты](diagrams/domain-access.md) и [задачи и записи работы](diagrams/domain-tasks.md) показывают проектную UML-модель классов. Роль и статус представлены перечислениями, участие — отдельным классом с составной идентичностью. В таблицах назначение роли реализуется связью user_roles; отдельный доменный класс для связи без собственных атрибутов не требуется.

Кратности UML должны сохраняться при реализации. Эти диаграммы не заменяют логическую модель и физическую схему; они не определяют DTO, контроллеры или окончательные JPA-аннотации.

## Проверка поддержки требований

| Требования / сценарии | Как поддерживаются моделью |
| --- | --- |
| FR-01, FR-02; UC-01, UC-02 | Пользователь, активность, хеш пароля и множество ролей; блокировка не удаляет ссылки. Проверка сессии относится к архитектуре. |
| FR-03; UC-03 | Отдельные типы и приоритеты с уникальными названиями и деактивацией. |
| FR-04, FR-05; UC-04, UC-05 | Единственный руководитель проекта и уникальное участие пользователя. |
| FR-06–FR-09; UC-06–UC-09 | Проект, автор и исполнитель задачи, календарный срок, фиксированный статус, версия карточки в физической модели. |
| FR-10, FR-11; UC-10, UC-11 | Независимое авторство комментариев и времени; записи сохраняются после переназначения. |
| FR-12–FR-14; UC-12, UC-13 | Группировка задач по статусу и текущему исполнителю; минут — по автору, включая отменённые задачи. Отчёт не требует собственной таблицы. |
| FR-15, FR-16; UC-14 | Email пользователя и актуальные данные задачи; сбой отправки не затрагивает сохранённое назначение. |
| BR-01–BR-03, BR-07–BR-12 | Связи позволяют проверить доступ и ограничения; правила нескольких объектов и текущего времени проверяет сервис в транзакции. |

Типы, длины, индексы и разграничение проверок приведены в [физической модели](database/physical-model.md).
