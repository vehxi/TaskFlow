## 2. Компоненты и зависимости

Код разделён в одном репозитории: Spring Boot в src/ и Gradle, React в frontend/. В разработке Spring слушает localhost:8080, Vite — localhost:5173 и проксирует /api на Spring. Браузер использует относительные URL одного origin, включая cookie и CSRF; разрешение CORS для произвольных адресов не требуется. Для поставки сначала выполняется npm-сборка интерфейса, затем Gradle включает frontend/dist в static исполняемого JAR. Spring отдаёт index.html для известных маршрутов React и отдельно обслуживает /api; API и отсутствующие файлы не подменяются SPA-страницей. PostgreSQL и SMTP-приёмник остаются внешними зависимостями.

[Диаграмма компонентов](diagrams/architecture-components.md) показывает слои и внешние связи. [Последовательность команды и уведомления](diagrams/architecture-command.md) отдельно раскрывает границу транзакции и отправку письма.

| Компонент | Ответственность |
| --- | --- |
| SecurityFilterChain и CurrentUserFilter | Сессия, CSRF, актуальная активность и роли пользователя; JSON-ответы 401/403. |
| React-клиент | Маршруты, формы, состояния загрузки, ошибки и отображение доступных действий. |
| Клиент API | Относительные fetch-запросы, cookie сессии, получение CSRF, обработка ошибок без автоматического повтора команд. |
| REST-контроллеры | Входные DTO, статусы, заголовки и выходные DTO из [контракта API](api-contract.md). |
| CommandCoordinator | Вызов транзакционного сервиса, получение результата commit, попытка уведомления и объединение результата для HTTP-ответа. Сам координатор не транзакционный. |
| Прикладные сервисы | Полномочия на объект, бизнес-правила, блокировки, транзакции, проверка версии и преобразование результата в DTO. |
| Репозитории JPA | Ограниченные доступом выборки, запись и блокировки; сущности не выходят за слой сервиса. |
| ReportService и ExcelExportService | Согласованный снимок и расчёт показателей; формирование файла из подготовленного ReportDto. |
| MailNotificationService | Отправка готового снимка уведомления через SMTP, безопасная запись результата и возврат SENT/FAILED. |

Пакеты планируются по функциям: security, users, references, projects, tasks, reports, notifications; внутри функций — web, service, repository, domain и dto по необходимости. Общие config и error содержат конфигурацию и обработку ошибок. Корневой пакет — ru.vehxi.taskflow. Зависимости компонентов передаются конструкторами. Сервисы не зависят от HttpServletRequest и React. REST-контроллеры вызывают сервисы; React получает только DTO. SpaController возвращает статический entry point и не выполняет бизнес-операций.

spring.jpa.open-in-view=false: нужные данные загружаются и переводятся в DTO в сервисе, пока доступна транзакция. Обратные связи JPA и password_hash не сериализуются в HTTP. Все публичные классы, методы и интерфейсы документируются Javadoc по NFR-09. Задача Gradle javadoc должна проходить с проверкой doclint; после проверки результат публикуется в docs/javadoc для просмотра из репозитория и обновляется вместе с соответствующим кодом.

## 3. Аутентификация и авторизация

Вход выполняет Spring Security по нормализованному email и паролю через POST /api/session (application/x-www-form-urlencoded). Успех возвращает 204, неверные реквизиты — JSON 401; после входа React получает новый CSRF и /api/me. Пароль хранится через PasswordEncoder; выбран DelegatingPasswordEncoder с bcrypt для новых записей и префиксом алгоритма. Стоимость хеширования проверяется на целевом окружении; длина пароля ограничивается с учётом байтового предела bcrypt. Исходный пароль не возвращается и не журналируется. Основание — [контракт PasswordEncoder](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/password-encoder.html).

Сессия хранится в памяти одного экземпляра приложения; после перезапуска нужен повторный вход. Cookie HttpOnly, SameSite=Lax; Secure включается при HTTPS. Таймаут бездействия — 30 минут. Успешный вход меняет идентификатор сессии; POST /api/session/logout с CSRF завершает сессию и возвращает 204. Для демонстрации локально допустим HTTP на loopback; внешнее развёртывание использует HTTPS.

Активность и роли заново загружаются по идентификатору пользователя для каждого защищённого запроса, а не только при входе. CurrentUserFilter после загрузки SecurityContext и до авторизации обновляет authorities; при блокировке инвалидирует сессию и очищает контекст. Командный сервис повторно проверяет инициатора внутри транзакции с дисциплиной блокировок. Поэтому открытая ранее сессия не сохраняет отозванные права. Запрос, уже завершившийся до блокировки, не отменяется задним числом.

Защита CSRF действует на вход, выход и JSON-команды с сессионной cookie. Клиент получает токен через API и передаёт X-CSRF-TOKEN; секреты сессии не хранятся в localStorage. GET /api/csrf выдаёт текущий токен с Cache-Control: no-store; после входа и выхода клиент запрашивает новый токен. Изменяющие GET не вводятся. Механизм соответствует [документации CSRF Spring Security](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

Грубое ограничение маршрутов дополняется серверной проверкой объекта. AccessPolicy проверяет руководство проектом, назначение задачи и участие; репозитории сразу ограничивают списки доступной областью. Администратор без дополнительных ролей не читает проекты и отчёты. Роль руководителя не открывает проекты другого руководителя. Пользователь с несколькими ролями получает объединение разрешений с сохранением объектных ограничений.

Содержимое недоступного объекта скрывается ответом 404; действие, запрещённое самой ролью, возвращает 403 без загрузки чужих данных. Нет входа или запись заблокирована — JSON 401 для API; React очищает состояние пользователя и показывает вход. Статическая оболочка SPA доступна без входа и сама по себе не предоставляет доступа к данным. Входные authorId, managerId, projectId у редактируемой задачи, даты создания и произвольные роли из недоверенного DTO не определяют полномочия. Неизвестные поля командного JSON отклоняются, чтобы случайная подмена поля не выглядела успешной.

## 4. Команды, транзакции и конкурентные изменения

Каждая изменяющая бизнес-операция — отдельный публичный метод сервиса с @Transactional. Ошибка проверки откатывает все изменения; внешнее SMTP-взаимодействие находится после возврата из транзакционного proxy. Чтение выполняется в readOnly-транзакциях; readOnly само по себе не является запретом SQL-записи.

Для изменяемых сущностей используется @Version. Команда обязана передать ожидаемую версию из карточки, которая сравнивается с текущей под блокировкой. Блокировка не заменяет это сравнение: она лишь упорядочивает параллельное выполнение. Конфликт — 409; интерфейс предлагает перезагрузить карточку, не повторяя команду автоматически. Запрос неизменённого статуса не меняет версию и не отправляет письмо.

Следуется общий порядок [физической модели](database/physical-model.md): затронутые пользователи по id → типы, затем приоритеты по id → проект → задача. Инициатор входит в набор блокируемых пользователей. Если для определения набора нужны предварительные чтения, после получения блокировок связи и права проверяются заново; изменившийся набор приводит к отмене попытки и ограниченному внутреннему повтору с новым чтением. Блокировки JPA задаются через PESSIMISTIC_WRITE у соответствующих методов репозитория; механизм поддерживается [Spring Data JPA](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html).

| Операция | Атомарные проверки и изменения |
| --- | --- |
| Пользователь и роли | Блокировка пользователя; минимум одна роль; запреты BR-03; изменение user_roles и увеличение version пользователя вместе. Блокировка учётной записи сохраняет историю. |
| Состав проекта | Блокировки затронутых пользователей и проекта; действующая роль, активность, отсутствие дубликата; запрет исключения при незавершённых задачах; изменение связи и version проекта вместе. |
| Создание задачи | Активность и полномочия инициатора, участие и роль исполнителя, доступность справочников; автор и проект задаются сервером; статус NEW. |
| Редактирование / статус | Актуальная версия задачи, разрешённое состояние, действующее назначение по BR-02; при открытии статус и новое назначение сохраняются одной транзакцией. |
| Комментарий / время | Блокируется родительская задача; сверяются ожидаемая версия, доступ и незакрытое состояние; добавляется запись и условным UPDATE tasks SET version = version + 1 WHERE id = :id AND version = :expected увеличивается версия задачи. Параллельное закрытие или переназначение не обходят проверку. |
| Справочники | Блокируется значение; новые назначения используют ту же блокировку. Деактивация не ломает старые ссылки. Уникальность БД проверяется и после предварительной проверки сервиса. |

Для изменений связей ролей, состава проекта и добавления дочерних записей версия родителя увеличивается отдельным условным UPDATE с проверкой числа изменённых строк. Такие команды не совмещают этот шаг с автоматическим JPA-увеличением той же версии: состояние persistence context синхронизируется после SQL, а DTO получает уже обновлённую версию. В обычном изменении полей сущности действует @Version. Конкретная реализация проверяется интеграционными тестами, чтобы ответ не содержал старую версию и не происходил двойной increment.

Для команды с конфликтом версия не подменяется последней автоматически. Повтор после deadlock/lock timeout ограничен и не скрывает бизнес-конфликт; если безопасное выполнение не удалось, API возвращает 409 с кодом RETRY_REQUIRED. Окончательные JPA-запросы и таймауты проверяются интеграционными тестами на PostgreSQL.

Clock и ZoneId передаются в сервисы как зависимости; LocalDate.now(clock.withZone(zone)) определяет текущую дату. Невалидные даты и дробные минуты отклоняются до сохранения. Положительное целое хранится в integer; сумма вычисляется в bigint. Идентификатор автора берётся из актуального контекста безопасности.

## 5. Отчётность и Excel

ReportService проверяет руководство проектом, получает данные в readOnly-транзакции REPEATABLE_READ и формирует неизменяемый ReportDto. Все запросы одной сводки читают один снимок. Счётчики задач и минуты агрегируются отдельно; комментарии не участвуют в суммировании. Задачи группируются по текущему исполнителю, время — по автору записи, включая отменённые задачи. Формулы прогресса и просрочки соответствуют BR-04–BR-06; пустой проект даёт нули.

ExcelExportService создаёт .xlsx из того же ReportDto после завершения чтения БД. Файл содержит название проекта, дату формирования в зоне приложения, итоговые показатели и детализацию. Количества и минуты записываются числовыми ячейками; текст проекта и имена пользователей — строковыми, не формулами. Формат отображения прогресса соответствует одному знаку после запятой. Workbook и потоки закрываются.

Экспорт разрешён прямым запросом только руководителю своего проекта; он не зависит от того, был ли ранее открыт экран отчёта. Два отчёта в разные моменты могут отличаться из-за изменений; сравнение чисел с экраном выполняется на одном наборе данных. Ответ имеет application/vnd.openxmlformats-officedocument.spreadsheetml.sheet и безопасное Content-Disposition; персональные ответы и отчёты не кэшируются публично.

## 6. Уведомления после commit

CommandCoordinator вызывает отдельный транзакционный CommandService. Сервис возвращает CommandResult с DTO сохранённых данных и необязательным снимком письма: taskId, title, projectName, dueDate, recipientEmail, ссылка, тип события. Возврат из proxy означает успешный commit. Lazy JPA-ссылки в снимок не передаются.

Только после этого координатор вызывает MailNotificationService синхронно в том же HTTP-запросе. Настройки соединения, чтения и записи SMTP имеют конечные таймауты; исходно 2000, 3000 и 3000 мс. Наличие таймаутов учитывает [рекомендации Spring Mail](https://docs.spring.io/spring-boot/reference/io/email.html). Ошибка почтового сервиса перехватывается вне бизнес-транзакции, регистрируется без паролей и SMTP-учётных данных; ответ остаётся успешным для сохранённой команды, но содержит notificationStatus=FAILED и понятное предупреждение.

Статусы: NOT_REQUIRED, SENT, FAILED. SENT означает принятие письма SMTP-сервером, а не подтверждённое чтение или попадание в ящик; доставка проверяется тестовым приёмником. При назначении и переназначении получатель — новый исполнитель, при смене срока — текущий. При одновременных изменениях формируется одно письмо. Повторное открытие без смены исполнителя, одинаковый срок, неизменённое назначение и отклонённая команда не создают событие.

HTTP-ответ при сбое SMTP сохраняет 201 или 200, соответствующий основной операции. Пользователь видит, что данные сохранены и письмо не отправлено. Автоматических повторов и фоновой очереди нет; сбой процесса между commit и отправкой может оставить сохранённое изменение без письма. Эти границы не обещают гарантированной доставки и соответствуют обязательной версии FR-15, FR-16. Тесты координатора проверяют, что после ошибки SMTP бизнес-данные существуют и транзакция БД завершена.

## 7. Обработка ошибок и валидация

DTO отделяют команды от представлений. Jakarta Validation проверяет обязательность, длины, email, даты и целые минуты; сервис — доступ и BR. Длины берутся из физической модели. React сохраняет допустимые поля формы и показывает сообщения у полей; пароль после отказа очищается. API использует единый ErrorResponse из [контракта](api-contract.md).

@RestControllerAdvice обрабатывает ошибки JSON, валидации и бизнес-операций. React переводит fieldErrors в сообщения форм, 401 — в повторный вход, 403 — в сообщение об отсутствии прав, 409 — в предложение обновить карточку. Ошибки фильтров Spring Security обрабатывают отдельные AuthenticationEntryPoint и AccessDeniedHandler с тем же форматом API. Ошибки unique/FK/optimistic lock переводятся в прикладные коды только после отката; пользователю не передаются SQL, стек или учётные данные. Неожиданный сбой получает requestId и безопасное сообщение; подробность остаётся в серверном журнале.

## 8. Окружение и миграции

Локальный запуск включает Spring Boot, Vite, отдельную PostgreSQL 16.15 и тестовый SMTP-приёмник. Для frontend требуется Node.js 24 LTS с npm; версии прямых зависимостей задаются в frontend/package.json, lockfile создаётся npm и сохраняется в Git после разрешения зависимостей. Для БД используется UTF-8 и локаль, корректно выполняющая lower для кириллицы; при подготовке окружения проверяются пары названий, отличающиеся регистром. Тестовый SMTP-приёмник привязывается к локальному интерфейсу. Режим real SMTP настраивается явно через внешние параметры TLS и аутентификации.

| Параметр | Назначение / исходное значение |
| --- | --- |
| DB_URL | JDBC URL БД приложения; указывается явно. |
| DB_USERNAME, DB_PASSWORD | Подключение приложения, без DDL-полномочий и владения схемой. |
| DB_MIGRATION_USERNAME, DB_MIGRATION_PASSWORD | Отдельное подключение Flyway с DDL-правами на схему приложения. |
| SERVER_PORT | Локально 8080. |
| APP_TIME_ZONE | Europe/Moscow. |
| APP_BASE_URL | Адрес интерфейса для ссылок в письмах; в разработке http://localhost:5173, при запуске JAR http://localhost:8080. |
| SMTP_HOST, SMTP_PORT | Адрес почтового сервиса; для локального приёмника порт задаётся его конфигурацией. |
| SMTP_USERNAME, SMTP_PASSWORD | Только для режима SMTP с аутентификацией. |
| SMTP_AUTH, SMTP_STARTTLS | Включаются явно для выбранного SMTP-сервера; тестовый приёмник может работать без них. |
| APP_BOOTSTRAP_ENABLED | По умолчанию false; включает одноразовую инициализацию администратора. |
| APP_BOOTSTRAP_EMAIL, APP_BOOTSTRAP_PASSWORD | Начальные данные администратора через внешнюю конфигурацию; пароль никогда не имеет значения по умолчанию. |

Связь переменных с spring.datasource.*, spring.flyway.*, spring.mail.* и app.* фиксируется в application.properties; секретов в этом файле нет. Таймауты SMTP и сеанса, open-in-view=false, ddl-auto=validate входят в обычную конфигурацию. Секретные файлы окружения, данные БД, логи, .gradle, build, node_modules и frontend/dist исключаются из Git; .mvn не используется. Gradle wrapper JAR и properties, gradlew и gradlew.bat сохраняются для воспроизводимой сборки.

V1__initial_schema.sql создаётся на основе [проектного DDL](database/schema.sql); внешняя BEGIN/COMMIT-обёртка при переносе удаляется, транзакцией управляет Flyway. Системные роли создаются миграцией. Новые миграции не изменяют уже применённые файлы; Hibernate проверяет схему и не создаёт её автоматически. Учётная запись миграций выдаёт приложению SELECT/INSERT/UPDATE на изменяемые таблицы и права USAGE/SELECT на identity-последовательности; для comments и time_entries — только SELECT/INSERT, для roles — только SELECT. DELETE предоставляется только на user_roles и project_members. Удаление доменных объектов и изменение старых комментариев/времени не публикуются в API; сервис дополняет ограничения SQL.

Bootstrap выполняется отдельной сервисной транзакцией после миграций при включённом флаге и отсутствии пользователя ADMIN. Для идемпотентности и защиты от параллельных запусков берётся отдельная транзакционная advisory-блокировка с фиксированным ключом инициализации, затем повторно проверяется наличие администратора. Запись roles не изменяется; подключению приложения не нужны UPDATE-права на неё. Транзакционная advisory-блокировка освобождается при завершении транзакции согласно [документации PostgreSQL](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS). Уже существующие пароли и роли не перезаписываются; конфликт email завершает инициализацию ошибкой. После успешной инициализации флаг выключается. Демонстрационные пользователи и проекты создаются только в отдельном demo-профиле; реальных данных и постоянных паролей в Git нет.

## 9. Проверки и порядок реализации

| Область | Проверка |
| --- | --- |
| Основа | Gradle toolchain 21, разрешение фиксированных зависимостей, запуск с пустой PostgreSQL, Flyway и JPA validate. |
| Доступ | Вход/выход, CSRF, изменение ролей и блокировка в открытой сессии, чужие объекты и экспорт; React и прямые запросы к REST API. |
| Правила | Все переходы статусов и роли; переназначение, неактивные справочники, дата работы в зоне приложения, неизменность авторства. |
| Конкурентность | Два изменения одной версии; закрытие против комментария/времени; исключение/отзыв роли против назначения; деактивация справочника против нового выбора. |
| Отчёт | 50,0% на контрольных данных, сумма 75 минут, нулевой проект, отсутствие размножения сумм при нескольких комментариях; файл читается обратно через POI. |
| Почта | Не требуется / успех / отказ; адресат и одно письмо при двух изменениях; сохранение данных при недоступном SMTP, отсутствие бизнес-транзакции во время отправки. |
| Интерфейс | Ширины 375 и 1440 CSS-пикселей; формы и ошибки; текст пользователя экранируется; допустимые действия доступны с клавиатуры. |

Интеграционные тесты используют отдельную PostgreSQL через Testcontainers и требуют Docker.

Порядок разработки: wrapper и конфигурация → миграция и сущности → React-клиент, вход и пользователи → проекты и участие → задачи и назначения → статусы, комментарии и время → справочники → отчёты, экспорт и почта → сквозная проверка. Таблицы справочников присутствуют с первого запуска, а временное наполнение для демонстрации не попадает в обычный профиль.

## 10. Структура React-клиента

frontend/src/api содержит типы DTO и клиент HTTP; app — состояние сеанса и маршрутизацию; features — экраны отдельных функций; компоненты используют CSS Modules и общие токены оформления. Логика прав на клиенте отвечает за навигацию и доступность кнопок, а сервер независимо проверяет каждый запрос. Неподдерживаемые функции не заполняются фиктивными рабочими данными.

Vite и React выбраны для отдельного интерфейса поверх существующего Spring API; SSR и серверные компоненты React для этого приложения не требуются. Основания: [сборка React с Vite](https://react.dev/learn/build-a-react-app-from-scratch), [конфигурация прокси Vite](https://vite.dev/config/server-options#server-proxy).
