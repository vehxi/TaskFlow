# Физическая модель PostgreSQL 16

Модель реализует [логическую структуру](../data-model.md). Выбрана PostgreSQL 16: локально доступна версия 16.15, а требуемые ключи, ограничения, транзакции и индексы поддерживаются этой веткой. Точная версия развёртывания и способ запуска будут зафиксированы при подготовке приложения.

Каноническое описание таблиц, значений по умолчанию, ограничений и индексов находится в [schema.sql](schema.sql). Это проект DDL для пустой тестовой БД, а не уже подключённая миграция приложения. При реализации он переносится в начальную версионируемую миграцию.

Схема разделена на [доступ и проекты](../diagrams/physical-access.md) и [задачи и учёт](../diagrams/physical-tasks.md). На диаграммах показаны ключевые поля; полный состав определяется DDL и словарём ниже.

## Общие решения

- Самостоятельные объекты имеют ключ bigint с GENERATED ALWAYS AS IDENTITY. Роль идентифицируется кодом; связи ролей и участников — составной парой ключей.
- Все столбцы обязательны. Пустые описания разрешены; пустые имена, названия, email, хеш пароля и комментарии запрещены.
- У изменяемых объектов users, projects, tasks, task_types и task_priorities есть неотрицательная version. Приложение сравнивает ожидаемую версию и увеличивает её при изменении; SQL DEFAULT сам по себе этого не делает.
- Момент создания хранится как timestamptz и соответствует Instant в Java. Срок задачи и дата работы — date / LocalDate. Они не переводятся между часовыми зонами; текущая дата для проверок получается в зоне приложения (исходно Europe/Moscow).
- Значения статусов: NEW, IN_PROGRESS, DONE, CANCELLED. Роли: ADMIN, MANAGER, EXECUTOR. Коды фиксированы и не зависят от русских подписей интерфейса.

Различие date и timestamptz соответствует [документации PostgreSQL](https://www.postgresql.org/docs/16/datatype-datetime.html).

## Словарь таблиц

Длины строк и текста — проектные ограничения; они должны совпадать с DTO и сообщениями валидации при реализации. Описание допускает до 10000 символов, комментарий — до 5000. Количество минут одной записи ограничено диапазоном положительного integer, без дополнительных ограничений «за день».

| Таблица | Поля и типы | Ключи и особенности |
| --- | --- | --- |
| users | id bigint; name varchar(120); email varchar(254); password_hash varchar(255); active boolean; version bigint; created_at timestamptz | PK id; UNIQUE email. Email хранится в нижнем регистре без крайних пробелов. active=true, version=0, created_at=CURRENT_TIMESTAMP по умолчанию. |
| roles | code varchar(16) | PK code; CHECK по трём кодам. DDL создаёт все три роли. |
| user_roles | user_id bigint; role_code varchar(16) | PK (user_id, role_code); FK на users и roles. Минимум одна роль у пользователя проверяется сервисом в общей транзакции создания/изменения. |
| projects | id bigint; manager_id bigint; name varchar(200); description text; version bigint; created_at timestamptz | PK id; FK manager_id → users. description='', version=0, created_at=CURRENT_TIMESTAMP по умолчанию. Название не обязано быть уникальным. |
| project_members | project_id bigint; user_id bigint; joined_at timestamptz | PK (project_id, user_id); FK на projects и users; joined_at=CURRENT_TIMESTAMP. Это действующий состав, не журнал участия. |
| task_types | id bigint; name varchar(80); active boolean; version bigint | PK id; уникальный индекс lower(name); крайние пробелы в хранимом имени запрещены. active=true, version=0. |
| task_priorities | id bigint; name varchar(80); active boolean; version bigint | Те же правила, что у task_types; уникальность независима для каждого справочника. |
| tasks | id bigint; project_id, author_id, assignee_id, type_id, priority_id bigint; title varchar(200); description text; due_date date; status varchar(16); version bigint; created_at timestamptz | PK id; пять FK на проект, пользователей и справочники. description='', status=NEW, version=0, created_at=CURRENT_TIMESTAMP. CHECK ограничивает набор статусов, но не переходы. |
| comments | id bigint; task_id bigint; author_id bigint; body text; created_at timestamptz | PK id; FK на tasks и users; непустой текст до 5000 символов; created_at=CURRENT_TIMESTAMP. Автор и время определяются сервером. |
| time_entries | id bigint; task_id bigint; author_id bigint; work_date date; minutes integer; created_at timestamptz | PK id; FK на tasks и users; CHECK minutes > 0; created_at=CURRENT_TIMESTAMP. work_date задаётся пользователем, created_at фиксирует момент ввода. |

Приложение нормализует email и крайние пробелы имён справочников перед проверкой и сохранением; БД отклоняет ненормализованное значение. Уникальность названий справочников без учёта регистра обеспечивается [индексом на выражении lower(name)](https://www.postgresql.org/docs/16/indexes-expressional.html). Она проверяется и для неактивных значений: повторное создание имени не заменяет деактивированную запись. Для кириллицы окружение БД должно использовать UTF-8 и согласованную локаль с корректным lower; локаль фиксируется и проверяется при развёртывании.

## Целостность и правила удаления

Все FK используют ON DELETE RESTRICT: автоматического удаления проектов, задач, записей работы или исторических пользователей нет. Управление приложением не предоставляет физическое удаление пользователей, проектов и задач; пользователь блокируется, задача отменяется. Комментарии и время доступны только для добавления и чтения. Для справочников используется деактивация; используемые значения не удаляются.

Связующую строку user_roles разрешено удалить при допустимом отзыве роли, строку project_members — при допустимом исключении участника. Проверки незавершённых задач и руководимых проектов выполняются до удаления. Пользователь остаётся адресатом FK из истории.

RESTRICT защищает существующие ссылки, но не запрещает удаление несвязанной строки или изменение комментария прямым SQL. Ограничения пользовательских операций реализуются сервисом и правами подключения; учётная запись приложения не получает полномочий владельца схемы. Политика миграций и прав подключения уточняется в архитектуре.

## Какие правила обеспечивает БД, а какие — приложение

CHECK в PostgreSQL подходит для условий строки; проверки связанных строк не следует подменять таким ограничением. Это разграничение опирается на [документацию ограничений PostgreSQL](https://www.postgresql.org/docs/16/ddl-constraints.html).

| Правило | БД | Сервис приложения |
| --- | --- | --- |
| Обязательные ссылки, уникальность email, роли и участия | NOT NULL, PK, FK, UNIQUE | Понятные ошибки и предварительная проверка; обработка конфликта уникальности при сохранении. |
| Типы полей, длины, непустой текст, положительные минуты | Типы, CHECK, varchar(n) | Валидация DTO без молчаливого округления или обрезания. Дробное число минут отклоняется до записи. |
| Активность, роль и участие исполнителя — BR-02 | FK подтверждает существование пользователя | Проверка в момент создания, назначения, начала работы и повторного открытия. Историческое назначение допускается без текущего участия. |
| Непустой набор ролей и допустимость отзыва / исключения — BR-03 | Составные ключи запрещают дубликаты | Общая транзакция; проверить незавершённые задачи и руководимые проекты. |
| Доступ к объекту и авторство — BR-01, FR-10, FR-11 | FK на существующего автора | Текущий пользователь определяется из сессии; входной author_id не считается доверенным. |
| Переход статуса, закрытая задача — BR-10 | CHECK ограничивает четыре значения | Проверка таблицы переходов, роли и текущего статуса перед записью. |
| Дата работы не в будущем — BR-07 | date хранит календарную дату | Сравнение с текущей датой в зоне приложения, без зависящего от часов CHECK. Прошедший срок задачи допустим для хранения и отчётов. |
| Деактивация справочника — BR-08 | FK сохраняет использованное значение | Новое назначение неактивного значения запрещено; прежнее при изменении другого поля сохраняется. |
| Отказ целиком и конфликт карточки — BR-09, BR-12 | Транзакции, поле version | Атомарная проверка version и сохранение; связанные изменения откатываются вместе. |
| Уведомления — BR-09, BR-11 | Основная операция коммитится отдельно от отправки | Отправка после commit; одно письмо при смене срока и исполнителя, отсутствие повтора без события; ошибка не откатывает данные. |

## Согласованность при одновременных изменениях

Одной проверки в форме недостаточно. При реализации изменения задачи выполняются в транзакции с проверкой ожидаемой version. Запрос обновления должен затронуть ровно одну строку; отсутствие совпадения означает конфликт, а не разрешение записать поверх чужих изменений.

Изменение набора ролей увеличивает version пользователя, изменение состава участников — version проекта в той же транзакции. Проект и автор уже созданной задачи, авторы комментариев и времени, моменты создания не редактируются пользовательскими операциями. Новые значения этих полей определяет сервер при создании соответствующей записи.

Добавление комментария или времени также проверяет версию и актуальный статус родительской задачи. В одной транзакции резервируется изменение версии задачи и сохраняется дочерняя запись. Поэтому закрытие или переназначение, выполненное параллельно, не позволит добавить запись на основании устаревшей карточки.

Операции назначения, отзыва ролей, блокировки и исключения участника должны использовать общую дисциплину блокировок: сначала затронутые пользователи в порядке id, затем значения справочников, проект и задача. Внутри каждой группы порядок также фиксируется по ключу. Прочитанные до блокировки связи повторно проверяются; при изменении набора нужных блокировок операция перезапускается. Все пути изменения обязаны соблюдать этот порядок. Блокировка пользователя связывает проверку его ролей с их изменением, блокировка проекта — проверку участия с исключением. Деактивация справочника использует ту же блокировку, что новое назначение значения.

Это требование к реализации сервисов, а не уже действующий механизм DDL. Точный механизм JPA-блокировок определяется на этапе архитектуры и проверяется конкурентными интеграционными тестами.

## Индексы и запросы

PK и UNIQUE уже создают необходимые уникальные индексы; повторные индексы на те же ключи не добавляются. Дополнительные индексы определены в DDL:

| Индекс / группа | Назначение |
| --- | --- |
| ix_user_roles_role | Отбор пользователей по роли. |
| ix_projects_manager | Список проектов под управлением пользователя. |
| ix_project_members_user | Проекты участника; порядок PK покрывает состав конкретного проекта. |
| ix_tasks_project_status_due | Задачи проекта, статусы и отбор по сроку с учётом ведущих полей индекса. |
| ix_tasks_assignee_status_due | Назначенные задачи исполнителя и контроль незавершённых назначений. |
| ix_tasks_author, ix_tasks_type, ix_tasks_priority | Поиск зависимостей и проверка ссылок на автора и справочники. |
| ix_comments_task_created | Чтение комментариев задачи в порядке created_at, id. |
| ix_comments_author | Ссылки на авторов комментариев. |
| ix_time_entries_task | Сумма времени задачи и выборка записей проекта через задачи. |
| ix_time_entries_author_date | Группировка времени по автору и дате; ссылки на пользователя. |

Это исходный набор, а не доказательство оптимального плана любого запроса. После реализации индексы проверяются на фактических запросах и данных.

Счётчики задач агрегируются по tasks, минуты — отдельно по time_entries с последующим объединением результатов. Прямое соединение задач с несколькими комментариями и записями времени без предварительной агрегации размножит строки и исказит суммы. Количество задач группируется по текущему assignee_id, время — по неизменяемому author_id записи. Суммы рассчитываются в bigint. Один экранный отчёт или файл экспорта строится на согласованном снимке данных (один запрос либо транзакция REPEATABLE READ); два запроса в разные моменты могут законно показать разные результаты.

## Статус проверки

16 ноября 2026 года выполнены статические проверки: в DDL определены десять таблиц и 50 столбцов; ссылки FK ведут в существующие поля; имена и типы полей физических диаграмм согласованы с DDL; ссылки между документами и на UML-классы корректны. Проверка не заменяет разбор и исполнение SQL сервером или визуальный рендер Mermaid.

Попытка создать отдельный тестовый кластер локальной PostgreSQL 16.15 остановилась на initdb: среда запрещает создание shared memory (shmget: Operation not permitted). SQL не применялся к существующим базам. Выполнение DDL, негативные проверки ограничений и визуальный рендер диаграмм остаются для проверки при реализации миграции. Схема сама по себе не реализует права доступа, переходы статусов, optimistic locking или доставку писем.
